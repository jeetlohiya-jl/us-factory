# Cirkla Factory OS — Performance Audit

Date: 2026-09-03
Scope: page-load / data-fetch latency, target <200ms for normal loads.
Method: seeded local Postgres (factory_os @ localhost:5432, postgres/postgres) with
representative ~1–2-year data volume, then measured real query plans (EXPLAIN
ANALYZE), raw SQL timing (psql \timing), and end-to-end ORM query+hydrate+serialize
timing via a script that instantiates the app's real SQLAlchemy models/session and
calls the exact same query-building code the routers use. Frontend was audited by
reading `src/lib/api.ts` and page components; the Supabase-direct queries could not
be timed live (no local PostgREST instance available in this environment), so their
cost is bounded from below by the equivalent raw-SQL/ORM timings measured here —
PostgREST executes structurally equivalent or costlier SQL (nested-resource JSON
aggregation) over an additional HTTP hop, so real numbers are at least as bad.

## Findings, ranked by impact

### 1. Material Consumption list — 3,000–5,500ms server-side, 1.6MB payload (CRITICAL)

**Where:** `backend/app/api/material_consumption.py:37-93` (`_q()` / `list_material_consumption`), mirrored by the code path actually serving the frontend, `frontend/src/lib/api.ts:395-420` (`listMaterialConsumptionSb`).

Both implementations fetch **every** `MaterialConsumption` row with a 3-level-deep
join fan-out (`machine_entries` → `pallets` → `pallet`, plus `production_run` →
`ipqc_record`), with no `LIMIT`, then filter by search/category/date/status in
Python/JS on the fully-materialized list. This is exactly the pattern flagged in
the task description.

**Measured evidence** (real ORM query against the seeded DB, 4,000 MC records / 5,938
machine entries / 17,894 pallets):
- Raw SQL for the equivalent join (`EXPLAIN ANALYZE`): **149.7ms**, and it already
  spills to disk for the sort (`Sort Method: external merge Disk: 15792kB`).
- Full round trip through the app's actual query-building code
  (`db.query(...).options(joinedload(...)).all()`): **3,053–5,563ms wall time**
  across 3 runs — i.e. **~5s Python-side ORM row-hydration/dedup overhead** on top
  of the 150ms SQL, because the joined-collection fan-out returns ~18k raw rows
  that SQLAlchemy's identity map has to collapse back into 4,000 nested objects.
- Serialized JSON payload: **1,640,100 bytes (1.6MB)** for 4,000 list items that
  the UI only shows a handful of summary columns for.

**Impact:** every open of the Material Consumption list page (and its Supabase
equivalent) costs seconds, not milliseconds — 15–25x over the 200ms target — and
gets worse linearly as the factory accumulates more shift records over time.

**Fix:** paginate at the SQL level (`ORDER BY created_at DESC LIMIT 50 OFFSET …`,
same shape `inward_qc.py`/`inward_vehicle_inspections.py` already use correctly),
push search/category/date/status into `WHERE` clauses, and switch the collection
loads from `joinedload` to `selectinload` to avoid the join-fanout row explosion
this list never needed. The Supabase query needs the equivalent `.range()` +
server-side filter treatment.

### 2. RM/FG Storage Records list — 560–730ms server-side, 3.1MB payload (CRITICAL)

**Where:** `backend/app/api/rm_storage.py:52-67` and `backend/app/api/fg_storage.py:52-67` (identical `list_storage_records`), and the code path actually serving the frontend, `frontend/src/lib/api.ts:215-228` (`storageRecordsQuery`).

Same shape as #1: `db.query(StorageRecord).options(joinedload(pallet), joinedload(location), joinedload(source_qr_generation), joinedload(stored_by_user)).filter(storage_type=...).all()` with **no LIMIT**, then a Python/JS substring filter on `search` over the fully materialized list.

**Measured evidence** (6,975 rm storage records after seeding 15,000 total):
- Query+hydrate: **563–664ms** wall time across 3 runs.
- Serialized payload: **3,133 KB (3.1MB)** for a list view.

FG Storage's `list_storage_records` is byte-for-byte the same query shape against
the `fg` slice of `storage_records`, so it has the same defect at whatever row
count FG storage accumulates to.

**Fix:** same as #1 — SQL-level pagination + `WHERE storage_type = ... AND (search
conditions)`, `selectinload` only where a collection is actually needed (here it's
all `many-to-one`, so `joinedload` is fine once bounded by `LIMIT`).

### 3. Production Runs list — 195–276ms server-side + a second full-table query (HIGH)

**Where:** `backend/app/api/production.py:51-73` (`list_production_runs`), and the code path actually serving the frontend, `frontend/src/lib/api.ts:519-531` (`listProductionSb`) which additionally joins 4 levels deep (`material_consumptions` → `machine_entries` → `pallets` → `pallet`, plus `sku_version_ref`) with no `.range()`.

FastAPI's version loads every `ProductionRun` (no LIMIT) plus a **second** unbounded
query just to build a `has_fg_qr` lookup set — two full-table scans for a list that
should be one paginated query with an `EXISTS`/`LEFT JOIN` subquery.

**Measured evidence** (4,000 production runs):
- Query+hydrate: **195–228ms** (first query) — already over budget on its own
  before the frontend's much heavier Supabase join is even considered.
- Second (FG-QR-linked-ids) query adds another **~2–29ms**, small in isolation but
  entirely avoidable (folds into one query with a correlated subquery or a
  `LEFT JOIN ... IS NOT NULL`).
- The frontend's `PRODUCTION_LIST_SELECT` nests `material_consumptions(machine_entries(pallets(pallet(...))))` — the same join-fanout problem as #1, on every row of an unbounded list; not directly timeable here (no local PostgREST) but the underlying join shape is a superset of what was measured at 195-276ms server-side, so the real number is higher.

**Fix:** paginate, and derive `total_pcs_per_pallet`/`shipment_number` either at
write time (denormalize onto `production_runs`) instead of re-deriving them from a
nested join on every list read, or only compute them for the current page.

### 4. RM/FG QR Generation list — unbounded + Python-side date/sku filtering (HIGH)

**Where:** `backend/app/api/rm_qr.py:48-63` and `backend/app/api/fg_qr.py:47-63`, mirrored by `frontend/src/lib/api.ts:118-134` (`qrListQuery`).

`search` is pushed into SQL correctly (`ilike`), but `date` and `sku` are applied
in a Python list comprehension **after** `.all()` has already fetched every
matching-search row — and if `search` is empty, that's every row in the table.

**Measured evidence** (2,872 rm QR batches): query+hydrate **53–97ms** wall time for
what should be a <10ms paginated query (compare to Inward QC's properly-paginated
list at 4–12ms for the same order of magnitude of underlying data, finding #7).
This one is currently the least severe of the unbounded lists only because
`qr_generation_records` itself is smaller than `pallets`/`storage_records` — it
will not stay that way as the factory accumulates RM/FG batches.

**Fix:** push `date`/`sku` into the `WHERE` clause (`func.cast(created_at, Date) =
:date`, `sku_code_snapshot.ilike(...)`) and add `LIMIT`/`OFFSET` pagination
matching the QC/Vehicle-Inspection list pattern.

### 5. IPQC list (Supabase-direct) — fully unbounded, all filtering client-side (HIGH)

**Where:** `frontend/src/lib/api.ts:696-708` (`listIpqcSb`).

`supabase.from("ipqc_records").select(IPQC_LIST_SELECT).order("created_at", {ascending:false})`
has **no `.range()`/`.limit()` at all** — it fetches the entire `ipqc_records`
table to the browser on every visit to the IPQC page, then filters
date/shift/status/search in JavaScript. There is no FastAPI equivalent to compare
against (IPQC list/detail is Supabase-only by design per the hybrid-architecture
split), so this is the primary code path and it has no pagination whatsoever.

**Measured proxy:** the underlying table shape (4,000 `ipqc_records`, 8,030
`ipqc_check_blocks`, 64,240 `ipqc_block_defects`) is comparable in row count to
Material Consumption (#1); an unbounded fetch of this shape from Postgres/PostgREST
is expected in the hundreds-of-ms-to-seconds range as the table grows, for a page
that only ever needs 50 rows on screen at once.

**Fix:** add `.range(0, 49)` (or a real page-size control) and push `date`/`shift`/
`status`/`search` into PostgREST `.eq()`/`.ilike()` filters, same as
`listInspections`/`listQc` already correctly do (see finding #8 for the working
reference pattern).

### 6. RM/FG pending-pallets list — unbounded (MEDIUM)

**Where:** `backend/app/api/rm_storage.py:37-49` / `fg_storage.py:37-49`, and `frontend/src/lib/api.ts:168-181` (`pendingPalletsQuery`).

`db.query(Pallet).filter(pallet_type=..., lifecycle_status="pending_storage").order_by(created_at).all()`
— no LIMIT, Python-side `search` substring filter. Lower severity than #1/#2 today
because `pending_storage` is naturally a working-set (pallets waiting to be shelved
should clear out), but it has no upper bound and will scale with how far storage
falls behind production — worth fixing alongside #2 since it's the same file/same
pattern.

**Fix:** same pagination + `WHERE display_id ILIKE ... OR sku_code_snapshot = ...`
treatment.

### 7. Missing index on `created_at`/`stored_at` for every unpaginated list's ORDER BY (MEDIUM)

**Where:** `material_consumptions.created_at`, `storage_records.stored_at`,
`production_runs.created_at`, `qr_generation_records.created_at`,
`inward_qc_records.created_at`, `inward_vehicle_inspections.created_at` — none of
these have an index (checked against what `0007_performance_indexes.sql` and
`0010_database_hardening.sql` already cover — they added FK-column indexes only,
never touched these ordering columns).

**Measured evidence:** the `EXPLAIN ANALYZE` for finding #1's join showed
`Sort Method: external merge  Disk: 15792kB` — Postgres had to spill the
`ORDER BY created_at DESC` sort of 17,894 rows to disk because there's no index to
walk in order.

**Impact:** on its own, secondary to findings #1–#6 (those need pagination fixed
first — an index doesn't help a query that has no `LIMIT`, since every row still
has to be visited and sorted). But once pagination is added, `ORDER BY created_at
DESC LIMIT 50` without an index still means Postgres scans/sorts the *whole*
filtered set before taking the top 50; with `create index on material_consumptions
(created_at desc)` (and the equivalent on the other 5 tables), that same query
becomes an index-order scan that stops after 50 rows.

**Fix:** add btree indexes on all 6 columns above (a single-column `created_at`/
`stored_at desc` index each is enough — no composite needed unless a specific
filter+sort combination shows up as slow in the after-measurement).

### 8. `GET /api/v1/me` — 9 sequential permission queries instead of 1 (MEDIUM)

**Where:** `backend/app/api/me.py:26-41`.

```python
for module in MODULES:      # 9 modules
    row = db.query(ModulePermission).filter(user_id=..., module=module).first()
```

**Measured evidence:** 9 sequential single-row lookups took **115.64ms**; the
equivalent single query (`module.in_(MODULES)`) took **1.89ms** — a **61x**
difference for functionally identical data.

**Impact:** this endpoint is now called once per browser session (not once per
navigation — `frontend/src/lib/useMe.ts` already caches it client-side, a prior fix
worth noting as done-right), but that first call still gates the entire app's
initial render, and 115ms of pure round-trip overhead for 9 tiny indexed lookups is
avoidable for free.

**Fix:** replace the loop with one `db.query(ModulePermission).filter(user_id==...,
module.in_(MODULES)).all()`, then build the `perms` dict from that single result
set (defaulting any module not present the same way `_perm_dict(None)` already
does).

### 9. Frontend has no data-fetch caching layer at all (MEDIUM, compounds everything above)

**Where:** `frontend/src/lib/api.ts` — no SWR, no React Query, no `@tanstack/*`
package is installed (`package.json` confirmed), every `request()` call sets
`cache: "no-store"` explicitly, and every Supabase call is a bare one-shot
`supabase.from(...).select(...)` with no client-side result cache.

**Impact:** this isn't a bug in isolation — data here does change and staleness
matters — but it means every one of findings #1–#6 pays its full multi-hundred-
millisecond-to-multi-second cost **on every single navigation to that page**,
including back-and-forth navigation where the same list was just fetched seconds
earlier. `useMe.ts` (finding #8's context) already demonstrates the right pattern
(module-level cache + subscriber set) for slow-changing data; none of the list
endpoints get the same treatment.

**Fix:** once #1–#6 are paginated, add a lightweight cache (SWR or React Query) for
list/detail GETs with a short `staleTime` (e.g. 10–30s) and revalidate-on-mutation,
so navigating back to a list a user just left doesn't re-pay the full query cost.

### 10. QR pallet generation writes serially, one round trip per pallet (LOW-MEDIUM — write path, not a page load, included because it directly affects perceived Generate-QR button latency)

**Where:** `backend/app/domain/qr_generation_service.py:172-215` (`generate_pallets`).

```python
for _ in range(rec.quantity):
    display_id = pallet_service.next_pallet_display_id(db, ...)   # own query+flush
    pallet = models.Pallet(...)
    db.add(pallet); db.flush()
    pallet_service.generate_pallet_qr(db, pallet)                  # own work
    pallet_service.record_lifecycle_event(db, pallet, "generated", ...)
    pallet_service.record_lifecycle_event(db, pallet, "pending_storage", ...)
```

Each unit of `quantity` does its own `next_pallet_display_id` lookup (a counter
UPSERT — see `id_counters.next_seq`) plus its own `db.flush()`, for what is
typically a batch of 5–40 pallets per QR generation click (observed range in the
seeded data). This is a write endpoint, not a page load, but it's the interactive
action every RM/FG QR Generation "Generate" click waits on synchronously — not
included in the 200ms budget's primary scope, flagged as a secondary opportunity
since the task's "recomputing something on every read" and "N+1" callouts apply to
its write-time equivalent here.

**Fix:** batch-reserve the display-ID range with one counter UPSERT of
`quantity` (return a starting sequence number, use `seq..seq+quantity-1`), then
bulk-insert the `Pallet` rows and their lifecycle events with `bulk_save_objects`/
`add_all` + a single `flush()`.

## Lower-priority observations (not in the top-ranked list, worth a follow-up pass)

- `inward_qc.py:167` and `inward_vehicle_inspections.py:115` each run a *second*
  unfiltered `count(*)` query (`total_all`) purely to report the grand total
  alongside the filtered `matched_count` — cheap today (~1ms, confirmed in
  measurement #7's reference case) but duplicates a query that's identical shape to
  `matched` when no filters are active; low priority since it's already fast.
- `pallet_lifecycle_events` was intentionally left unseeded (0 rows) — no read
  path in the audited routers queries it in a list/loop, so it wasn't a
  measurement priority, but flag it if a future Pallet timeline/history view is
  added.
- No base64/embedded-image payloads were found anywhere in the schemas —
  `ImageOut`/`PalletOut`/`StorageRecordOut` all carry URL references
  (`storage_path`/`public_url`), not inline bytes. This is already done right and
  is not a finding.

## What was confirmed NOT to be a problem (so it isn't re-flagged)

- `inward_qc.py` `list_qc` and `inward_vehicle_inspections.py` `list_inspections`
  already do real SQL-level `WHERE` filtering + `ORDER BY ... LIMIT ... OFFSET`
  pagination. Measured at **4–12ms** wall time end-to-end against the same 4,000-row
  seeded table that finding #1's Material Consumption list takes 3–5.5 **seconds**
  against — this is the reference "good" pattern every other list endpoint in this
  audit should be brought up to.
- `frontend/src/lib/useMe.ts` already fixed a real prior redundant-fetch bug
  (module-level cache + subscriber pattern, one fetch per session instead of one
  per page) — good pattern, not re-flagged, and a model for finding #9's fix.
- Migrations `0007_performance_indexes.sql` and `0010_database_hardening.sql`
  already cover every foreign-key column that needed an index for join/filter
  performance — verified against `pg_indexes` on the seeded DB; no missing FK
  index was found beyond what's already there.
- `frontend/src/app/*/page.tsx` components already parallelize independent fetches
  with `Promise.all` (e.g. `material-consumption/page.tsx`, `rm-storage/page.tsx`,
  `production/page.tsx`) rather than waterfalling them — no sequential-fetch
  finding to report there.
- No polling/`setInterval` anywhere in the frontend.
